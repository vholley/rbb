---
name: clear
description: Remove the RBB records of changes that were merged into the target branch, in one commit, after the requester confirms which. Works whatever the merge strategy. In documents mode none, deletes the confirmed local record folders instead.
argument-hint: [target branch]
---

Arguments: $ARGUMENTS

1. Run the plugin workflow `rbb:clear-records` with the Workflow tool, with args `{"target": "<the first argument>"}`, leaving `target` out when there is no argument, and wait. Do not write or delete any file yourself. Until it returns, say only that it is finding the records: whether they are committed or kept only on this machine is known only from its result.
2. If it returned an error, show it as written, say that `/rbb:clear` runs it again once the cause is fixed, and stop. If it found no records, say that nothing needs clearing, that `/rbb:status` says where each change stands, and stop.
3. If the result says `documents` is `none`, the records exist only on this machine, as files git ignores, so there is no commit and a deletion is permanent: nothing restores them. List each change found, one line each, with its files. Ask once with `AskUserQuestion` which changes are done and should have their local records deleted ("Delete <change> (Recommended)" and "Not now" with one change; a multiple-choice question with several). Say that a confirmation may appear before anything is deleted (from Claude Code, or from a tool that holds deleting commands), and that nothing is removed unless they confirm it. Then run the workflow again with args `{"target": "<target>", "clear": [<the chosen changes>]}` and report what it returned: the changes deleted and the ones kept. Stop here.
4. Otherwise the records are committed. List each change it found, one line each: its name, and whether its approval commit is on the target (merged with a merge commit or a fast-forward) or only its files are (squash or rebase). Say that the records stay in the pull requests and in history, so one `git revert` of the clearing commit restores them.
5. Ask once with `AskUserQuestion`, with two questions:
   - Which changes to clear: with one change, "Clear <change> (Recommended)" and "Not now"; with several, a multiple-choice question with one option per change.
   - Where the commit goes: "On <target> (Recommended)" when `current` is the target, and "On a new branch from <target>, for a pull request". When `current` is not the target, offer only the new branch, or switching to the target first.
6. Before running it, say that a confirmation may appear before anything is deleted (from Claude Code, or from a tool that holds deleting commands), and that nothing is removed unless they confirm it. On their answer, run the workflow again with args `{"target": "<target>", "clear": [<the chosen changes>]}`, adding `"branch": "<a name>"` for a new branch. Name the branch by the project's convention when `.rbb/config.json` gives a prefix, otherwise `rbb-clear-records`.
7. Report what it returned: the changes cleared, the commit subject, and the branch. Never push. If they chose a new branch, say that `/rbb:pr` does not apply to it and that they can push it and open a pull request as for any other change. End with the next step, one line: `/rbb <request>` starts the next change, and `/rbb:status` says where any other change stands. When a step above shows an error, also say that `/rbb:clear` runs it again once the cause is fixed.
