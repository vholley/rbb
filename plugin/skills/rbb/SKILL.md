---
name: rbb
description: Run the whole RBB flow for one change - shape the goal, draft and approve the spec, build, check, and write the pull request body - stopping wherever a step asks the requester something. Given the name of an existing change, resumes it from where it stands; with no argument, lists the changes and asks which to resume or whether to start a new one.
argument-hint: [request, or the name of a change to resume]
---

Arguments: $ARGUMENTS

You run the steps in order by invoking RBB's own skills with the Skill tool, one at a time, each with its arguments as that skill expects them. Each skill asks its own questions and shows its own pages, exactly as written, never paraphrased or shortened; you add nothing to them. Stop the flow at the first error any step reports, showing it as written. Never post a pull request, push, or delete anything: the flow ends with the pull request body written.

1. If there is no argument, run the plugin workflow `rbb:status` with the Workflow tool, with args `{}`, and wait. If it found no change, ask for the request and wait, then continue at step 3 with it. Otherwise show its `lines` exactly as written, one per change. With exactly one change, say that you are resuming it and continue at step 2 with its name: no question. With several, ask once with `AskUserQuestion` which to resume: one option per change, labelled with the change name and its stage in a few words ("task-520: built, not checked"), and a last option "Start a new change". On a change, continue at step 2 with its name. On a new change, ask for the request and continue at step 3.
2. Decide whether this starts or resumes a change:
   - If the argument is one word of lowercase letters, digits and hyphens, and the folder `.rbb/<word>/` exists, it is the name of a change to resume. Run the plugin workflow `rbb:status` with the Workflow tool, with args `{"change": "<word>"}`, show its line as written, and continue at the step its stage calls for: `goal` or `goal ready` at step 4, `drafted` at step 5, `approved` at step 6, `changed`, `built` or `stale` at step 7, `checked` at step 8, `pr ready` or `merged` at step 9. A folder with no goal or spec starts over at step 3 with the request asked for.
   - If the argument is one such word and no folder `.rbb/<word>/` exists, it is a change name with no change behind it, not a request: say so, then do step 1 as if there were no argument (list the changes there are, and ask which to resume or whether to start a new one from a request you ask for).
   - Otherwise the argument is the request. Continue at step 3.
3. Invoke the skill `rbb:goal` with the request as its argument. It names the change, saves the goal and asks any question only the requester can answer. Note the change name it reports; every later step uses it.
4. If the goal still has open questions (the goal skill said so, or the status said `goal`), settle them without reshaping the goal: read `.rbb/<change>/goal.json`, ask its `questions` in one `AskUserQuestion` call, each as written, with the question's `options` as the choices, the recommended one first and labelled "(Recommended)", each option described by its `means`, and the recommended one's description adding the `because` and the `affects`; then run the plugin workflow `rbb:goal` with the Workflow tool, with args `{"change": "<change>", "request": "<the source_request from goal.json, verbatim>", "answers": [{"question": "<as written>", "answer": "<their answer>"}]}`. Never pass the change name as the request. Repeat while questions remain; an answer stands and is never asked again. When the status said `goal ready`, there is nothing to ask.
5. Invoke the skill `rbb:approve` with the change name. It drafts the spec when there is none, shows the page, asks for approval or a change, settles the commit style once per repository, and freezes the spec. Continue only once it reports the approval (a commit, or the hashes in documents mode `none`).
6. Invoke the skill `rbb:build` with the change name. If it reports that the builder stopped, show the reason as written and stop: the spec or an example needs the requester.
7. Invoke the skill `rbb:check` with the change name. It shows the review page.
8. Invoke the skill `rbb:pr` with the change name alone (never with `post`). It writes the body and shows it, and gives the commands to post.
9. End by saying where the change stands in one line: the body is written, and `/rbb:pr <change> post` opens the pull request when the requester asks. If the status in step 2 said the change is merged, say instead that its records await `/rbb:clear`.
